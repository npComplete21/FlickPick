# FlickPick

Movie ranking app. You import your watched films, rank them by pairwise
comparison, and get a scored, ordered list.

## Layout

Monorepo, one folder per deployable. Service boundaries are enforced by
folder / build / database separation, not by separate git repos.

| folder | port | database (host port) |
|---|---|---|
| `user-service` | 8081 | `flickpick_user` (5433) |
| `import-service` | 8082 | `flickpick_import` (5434) |
| `ranking-service` | 8083 | `flickpick_ranking` (5435) |
| `frontend` | 5173 | — |

Spring Boot 4.1 / Java 21 / Maven wrapper per service; React 19 + TypeScript +
Vite for the frontend. **DB per service** — no shared database. **No API
gateway yet**: the frontend calls all three services directly by absolute URL,
and each service allows CORS from `http://localhost:5173`.

## Running locally

```bash
docker compose up -d                      # the three Postgres containers
cd <service> && ./mvnw -q spring-boot:run # each service, in its own shell
cd frontend && npm run dev                # vite on 5173
```

Frontend checks: `npm run build` (tsc + vite) and `npm run lint` (oxlint).

## Gotchas that have already cost time

**Docker Compose containers are named `initial-poc-*`, not `flickpick-*`.**
Compose otherwise derives the project name from the directory you run it
from, so containers and volumes created in one worktree were invisible — and
port-conflicting — from every other checkout. `docker-compose.yml` now pins
`name: initial-poc` explicitly, so `docker compose up`/`ps`/`logs` work
identically from any directory. The odd name is historical (an early worktree
was called that) and is kept deliberately: the existing volumes
`initial-poc_*-db-data` hold the current dev data, and renaming the project
would silently start you on empty databases. Background:
`docs/build-log/03-docker-compose-project-naming.md`.

**JWT keys are per-machine and hand-copied.** `user-service` holds the RSA
private key and is the only service that can mint tokens (RS256). Its
`certs/*.pem` are gitignored and generated by `user-service/generate-keys.sh`.
`ranking-service` and `import-service` each hold a **committed** `public.pem`
to verify with. Regenerating User Service's keypair silently breaks token
verification everywhere else until you re-copy the public key across. This has
already caused one debugging detour.

**Spring Security intercepts more than you expect.** Two rules exist in every
service's `SecurityConfig` for non-obvious reasons: `/error` must be
`permitAll` (Boot forwards thrown exceptions there, and the forwarded request
re-enters the filter chain unauthenticated, silently replacing a 409 with an
empty 403), and `OPTIONS /**` must be `permitAll` (CORS preflights carry no
`Authorization` header, so the auth rule rejects them before MVC's CORS
handling runs, and the browser reports it as an opaque CORS error).

**Hibernate does not preserve the order you call setters in.** `ranked_movies`
has a unique `(user_id, rank_position)`, and Postgres checks it per row, not
at commit. `saveAllAndFlush` forces the UPDATEs ahead of a subsequent INSERT,
but gives you **no control over ordering among the UPDATEs themselves** — so
shifting `[4,3,2] -> [5,4,3]` throws a duplicate-key error if Hibernate emits
`3->4` before `4->5`. Iterating high-to-low does not help; it only controls
setter order, not SQL emission order.

Any code that renumbers positions must therefore stage through a disjoint
range first (`p -> -(p+2)`, flush, `-> p+1`), which is collision-free under
any flush order. `RankingService.finalizeInsertion` and
`evictSeedsOnceLibraryExists` both do this. This bug sat latent for weeks and
only surfaced once several films started being placed inside one transaction.

## Conventions

- **Schema is `ddl-auto: update`.** No Flyway/Liquibase yet, so entity changes
  apply automatically and dropped columns/tables linger in dev databases.
- **Every increment gets a build-log entry** at
  `docs/build-log/<service>/NN-topic.md`, recording the decision *and the
  alternatives rejected*, not just what was built.
- **`docs/PROJECT_STATUS.md`** is the resume-from-cold snapshot; keep it
  honest about what is merged vs. merely built.
- Feature branches + PRs to `main`; `.claude/` is intentionally untracked.
- Ranking Service stores a plain `userId`, never a foreign key to User — it
  does not own user data and will not join across a service boundary.
- **The `movies` catalog is shared across all users; a ranking queue is not.**
  The catalog is global so TMDb dedup works, which means it also holds films
  other people imported. A user's backlog must therefore be scoped through
  `UserLibraryEntry` (`findUnrankedInLibrary`), never drawn from `movies`
  directly — otherwise people get asked to rank films they have never seen,
  and it gets worse as more users import. The seed catalog is a fallback only
  for an account that has imported nothing, and seeds are evicted the moment
  a real library exists.
